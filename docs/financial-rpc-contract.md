# Phase 5 financial RPC contract

All `pay_*` RPCs are **service_role only**. The server verifies the current user before passing an actor UUID. The database rechecks the participant/admin relationship. Never call these with a browser Supabase client. Amounts are integer USD cents. `environment` is `sandbox` or `live`; these are isolated in unique keys.

- `pay_prepare_account(p_host_id uuid, p_environment text) -> jsonb`: `{operation_id, host_id, environment, account_id, transfers_active, payouts_active, requirements_due}`. Stable operation UUID is the Stripe account idempotency key. Actor must be a verified host. Server obtains email/name from its verified user/profile.
- `pay_attach_account(p_operation_id uuid, p_account_id text) -> void`: write-once account mapping.
- `pay_sync_account(p_account_id text, p_environment text, p_transfers_active boolean, p_payouts_active boolean, p_requirements_due jsonb) -> void`.
- `pay_reserve_checkout(p_actor_id uuid, p_booking_id uuid, p_environment text,p_policy_id uuid,p_terms_accepted boolean) -> jsonb`: reuse an active attempt or create one. Returns `{attempt_id,operation_id,booking_id,guest_id,host_id,listing_title,amount_cents,currency,host_account_id,commission_cents,policy_version,expires_at,attempt_state,session_id,url}`. Requires published listing, accepted booking, ready account, explicitly enabled policy and at least 31 minutes left. Expiry is the earlier of the booking deadline and 23 hours. No deadline extension.
- `pay_attach_checkout(p_attempt_id uuid,p_session_id text,p_payment_intent_id text,p_url text,p_expires_at timestamptz) -> void`: session write-once; `p_payment_intent_id` nullable. Persist even after network uncertainty; never generate a fresh attempt to retry.
- `pay_ingest_event(p_environment text,p_account_context text,p_event_id text,p_event_type text,p_object_id text) -> jsonb`: `{event_key,status}`. Unique environment/account/event; status `pending`, `failed`, `processed`. Repeated pending/failed events stay retryable.
- `pay_finish_event(p_event_key uuid,p_error text) -> void`: null error marks processed; non-null marks failed with bounded error text. Only call after canonical reconciliation succeeds.
- `pay_apply_payment(p_event_key uuid,p_attempt_id uuid,p_session_id text,p_payment_intent_id text,p_charge_id text,p_amount_cents integer,p_currency text,p_state text,p_processor_fee_cents integer) -> jsonb`: canonical states `processing`, `paid`, `failed`, `expired`; fee/charge/PI nullable while unavailable. Requires matching event environment and stored session. `paid` requires PI and Charge IDs and exact USD total. Returns `{state,booking_status}`. Never downgrade paid; duplicates are no-ops. A mismatch, duplicate successful payment, or late slot conflict becomes `quarantined` and freezes release. Only accepted verified payment confirms the booking.
- `pay_get_operation(p_operation_id uuid) -> jsonb`: account/checkout/settlement operation for safe retry. Null if unknown.
- `pay_read_booking(p_actor_id uuid,p_booking_id uuid) -> jsonb`: participant/admin-safe payment summary, independent refund/transfer states and eligible checkout URL for its guest.
- `pay_read_host(p_actor_id uuid,p_environment text) -> jsonb`: own account readiness and booking earnings ledger.
- `pay_read_admin(p_actor_id uuid,p_environment text) -> jsonb`: operator settlement queue, failed/quarantined attempts, disputes and bank payout records.
- `pay_complete_booking(p_actor_id uuid,p_booking_id uuid) -> void`: verified admin confirms completion only after experience end and verified payment.
- `pay_prepare_release(p_actor_id uuid,p_booking_id uuid,p_operation_id uuid) -> jsonb`: verified admin; completed booking, configured delay elapsed, exact entitlement known, no dispute/refund/unknown operation, account ready. Returns `{operation_id,kind:'transfer',booking_id,amount_cents,currency,destination,charge_id,transfer_group,state}`. One transfer operation per booking; caller keeps provided UUID stable on retry.
- `pay_prepare_refund(p_actor_id uuid,p_booking_id uuid,p_amount_cents integer,p_reason text,p_operation_id uuid,p_attempt_id uuid) -> jsonb`: verified admin; selects the exact charged attempt and reserves amount against prior refunds and creates a durable refund operation. Returns `{operation_id,kind:'refund',booking_id,amount_cents,currency,payment_intent_id,charge_id,state,reversal_operation}`. `reversal_operation` is null before transfer, otherwise `{operation_id,kind:'reversal',amount_cents,transfer_id,state}`. The refund and reversal are independent: do not delay an owed refund because recovery failed.
- `pay_record_operation(p_operation_id uuid,p_external_id text,p_state text,p_error text) -> void`: monotonic operation reconciliation; state `pending`, `succeeded`, `failed`, `unknown`. Store unknown after transport uncertainty and reconcile before any retry. Successful refund keeps original payment paid; full refund cancels the booking and may restore its founding credit only under the captured policy.
- `pay_sync_dispute(p_environment text,p_charge_id text,p_dispute_id text,p_state text,p_amount_cents integer) -> void`: canonical open/won/lost; any non-won dispute freezes release; review host recovery manually.
- `pay_sync_payout(p_environment text,p_account_id text,p_payout_id text,p_state text,p_amount_cents integer,p_currency text,p_arrival_date timestamptz) -> void`: host bank payout lifecycle only. Does not mark individual bookings paid out; payout-to-booking reconciliation is not inferred.

Commercial policy and founder enrollment use separate **verified-admin** commands. No policy, fees, terms, or host promotion is seeded. Supported explicit policy is separate charges/transfers after admin-confirmed completion, with a chosen delay; platform-absorbed or verified actual host processing cost; proportional commission refunds with nonrefundable actual processing deduction; founding terms begin at the agreed recorded activation and reserve free credits when checkout starts strictly before the frozen, configured calendar-month Miami cutoff. Quotes stay frozen if processing finishes later. Refund credit restoration is an explicit boolean. Owners must approve these semantics before enabling. Unsupported terms remain disabled, not guessed.

Founders keep the recorded reduced lifetime rate across later policies. The host’s frozen free-booking allowance uses reserved/consumed/released grants under the host lock. When remaining credits are in flight, an additional regular-fee attempt is blocked until they settle. Referral credits are separate operator-approved qualified-referral grants with an explicit policy size/cap; no automatic invites or referral claims.

## Additional integration commands

- `pay_checkout_terms(p_actor_id,p_booking_id,p_environment)` returns the exact total, current/reserved policy ID, version and cancellation text for the guest review step. Checkout reservation requires that same policy ID and explicit consent, storing its timestamp. A policy change between review and payment requires another review.
- `pay_sync_refund(p_environment,p_charge_id,p_refund_id,p_state,p_amount_cents,p_operation_id)` correlates canonical metadata to a reserved refund even if its webhook arrives before the API response is saved. External refunds are recorded and flagged for settlement review.
- `pay_sync_transfer(p_environment,p_transfer_id,p_amount_reversed,p_operation_id,p_amount_cents,p_charge_id,p_destination)` verifies exact amount/source/destination and correlates the reserved operation before recording success. An untracked external transfer against a known charge freezes further release.
- `get_booking_details` and `list_my_bookings` expose `payment_hold_active` so the UI does not expire a slot while Stripe could still collect.
- `pay_read_host` includes `commercial` (null before approval): current policy and the host's own recorded founding rate/window/credit counts. It is never available anonymously.

`quarantine_reason` may also be set on a paid attempt after an out-of-app financial adjustment. Paid history is preserved, but further transfer release is blocked. Reconcile the provider records and all recovery obligations through a trusted operator before clearing a hold; no automatic clear endpoint exists. Refunds of a quarantined duplicate charge do not reduce entitlement or create recovery against the valid charge. A terminal failed transfer requires a new reviewed operation; a stale original amount cannot be blindly retried after a refund.

## Configurable founding terms

Migration `20261012161729_configurable_founding_incentives.sql` is **applied to hosted Supabase**; the matching application is deployed at `53bf519`. It seeds no policy or promotion. The [owner proposal](launch-decisions-proposed.md) is not configuration.

- `admin_set_commercial_policy(p_settings jsonb)` keeps its signature and adds mandatory `founder_free_bookings` (integer 0–100), `founder_duration_months` (integer 1–24 calendar months), and `founder_cohort_cap` (integer 1–10000), alongside existing policy fields.
- `admin_enroll_founder(p_host_id uuid,p_environment text,p_started_at timestamptz,p_policy_id uuid)` replaces the three-argument signature. A verified admin must submit the displayed current policy ID; stale consent fails with `22023` after acquiring the environment cohort lock. The host must be verified and have a published listing. The timestamp records explicitly agreed activation; backdating requires the displayed terms to match the originally agreed terms.
- Policy saves and enrollments share environment advisory lock `72464`. The cohort cap counts all prior enrollments across policy versions in that environment. Each enrollment freezes its free-booking limit, duration, lifetime rate and refund-restoration rule. End time is exclusive at activation plus the configured calendar months in America/New_York.
- Existing policy rows backfill the historical ten-booking/six-month values and nullable legacy unlimited cohort; existing enrollments preserve exact start/end/rate/restoration terms. This compatibility backfill does not approve or seed a current offer. New policies require a positive explicit cohort cap.

## Scheduled expiry and payable deadlines

Hosted migrations `20261012161739_booking_expiry_sweep.sql` and `20261012161747_payable_booking_deadlines.sql` are applied. They add the following without choosing business deadlines; the matching application is deployed at `53bf519`:

- `expire_due_bookings(p_limit integer default 100) -> integer` is service-role-only, validates 1–100, and returns the number of newly persisted expirations. It skips financial holds and busy host advisory locks, rechecks effective status before updating, and writes a booking event; the existing trigger queues request-closed notification once. It does not call Stripe or release a possibly paid hold.
- The authenticated email worker invokes expiry before claiming up to five messages. An expiry error prevents claims. Disabled worker/scheduler means this sweep does not run automatically.
- New request/slot admission and host acceptance require more than 32 minutes before experience start, and payment policy configuration must allow at least 32 minutes. A requested booking closes no later than start minus 32 minutes. This technical margin is distinct from the existing 31-minute Checkout reservation guard and does not set the proposed 24-hour business windows.
